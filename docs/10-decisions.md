## D-030: Camp は CLI の忠実なリモコン。守りはネットワークと認証の層に任せる（2026-09-12）

本人の想定を明言してもらった（2026-09-12）: Camp は「このホストを AI の作業場にして、tailnet の中から快適に遠隔操作し、Vault も読み書きする」ためのもの。外に公開しない。tailnet が乗っ取られるなら Web UI どころでない問題で、別の層で対処する。

- **Camp を門番（エージェントを囲う安全境界）にしない。** エージェントは CLI で開いたときと同じ置き場・設定・ルール・フック・プラグインで動かし、Camp は止める・見せる・記録するに徹する。確認の度合いはセッションごとに本人が選び、既定は CLI と同じ（Phase 3.7、`dev/active/phase3.7-plan.md`）
- **理由**: 同じユーザーのものは Camp を通さず何でもでき（D-025 で受け入れ済み）、auto mode のエージェントも本人にできることは全部できる。Camp 側の囲いが守れるのは「マシンには入れず、画面にだけ入れた人」だけで、それはネットワークと認証の層で守るもの。囲いはエージェントを縛らず、CLI との差と合わせ続ける手間を増やしていた（D-029 の専用の置き場で、computer use が動かない・フックが走らない・履歴が Codex アプリに出ない・許したコマンドがネットワークに出られない、が出た）。スマホで承認を大量にさばくと中身を読まずに押しがちになり、エージェント自身の判定（auto mode）に任せたほうが安全なこともある
- **残す最低限**（緩めない）: tailnet の中だけ（funnel なし）。Camp 自身のログインと、別のサイトから操られない守り（Cookie は SameSite=Strict・HttpOnly、書き込みは Origin と Sec-Fetch-Site を照らす）。**ノートや AI の出力を HTML としてそのまま描かない**——セッションを起こせる同じ画面の中で細工された文章が動けば、tailnet を破られなくてもマシンを操れる。Web ならではの穴で、「別の層で守る」が及ばない。Phase 5 の編集面（Markdown の表示）で特に守る
- **残すもの**（エージェントを縛らずに役に立つ）: Camp を専用ユーザーで動かすこと（会話履歴の DB と監査ログを守る）・監査ログ・止めたあとの後始末の確かめ・承認の取り下げ・待ち行列・引き取り直し・許可リスト（起こす場所の入口として）。SSH の行き先の固定（D-028）は作ってあるので当面残し、これ以上足さない
- **確認の度合いは、起こしたときに効いたかを1回だけ照らす。途中の変化は止めずに記録して画面に出す**（2026-09-12、本人。Fable の設計レビューの論点）。Claude の plan mode、Codex の設定の変化や自動審査の開始でセッションを殺さない（CLI では止まらない）
- **覆したもの**: D-029 の「承認を関門にするため、Codex を Camp 専用の置き場で起こし、本人の rules と信頼済みの場所を持ち込まない」と「方針を Camp が決めて照らす」、「途中で方針が変わったら止める」。Codex は本人の `~/.codex` で起こし、方針は本人が選んだものだけを渡して照らす。D-029 の記録は消さずに残す

## D-028: SSH の向こうに起こす。常駐させず、行き先を固定し、ホスト鍵は受け入れない（2026-09-11）

本人の頼みで、Phase 3 で次に回した「SSH で他のホストにセッションを起こす」を入れた（Phase 3.5、`dev/active/phase3.5-plan.md`）。D-003（エージェントなし）のまま、実行面が `ssh <alias> <小さな sh>` を起こす。

- **許すときに行き先と、ssh が信じるホスト鍵を固定する。** D-026 は「`~/.ssh/config` を編集しただけで繋げる先が増えることはない」と約束したが、エイリアスだけを許すと、許したあとで HostName を書き換えれば同じ名前のまま別の先へ繋がる。許したときに `ssh -G` の hostname / user / port / proxyjump / proxycommand / hostkeyalias と、**known_hosts がその行き先について信じる鍵の指紋の全部**を控え、起こすたびに照らす。違えば繋がない。鍵が本体——ホスト鍵は経路（DNS・ProxyCommand）に関係なく向こうに証明させるものなので、信じる鍵が同じなら繋がる相手は許したときと同じ。`KnownHostsCommand` は切る。known_hosts に鍵の無い先は許せない。`~/.ssh` を読めるのは実行面だけなので、固定は実行面に読ませる。だから CLI（`campd ssh allow`）からは許せない（外すことはできる）
  - **当初は鍵を固定していなかった**（hostname などだけ）。`UserKnownHostsFile` や `HostKeyAlias` を書き換えれば、同じ名前・同じ hostname のまま別の鍵を信じさせられた。outer gate で codex が指摘し、直した。鍵を固定していない許可では起こさない（許し直す）
- **ホスト鍵を Camp は受け入れない**（`StrictHostKeyChecking=yes`・`UpdateHostKeys=no`）。初めての先は端末で一度 `ssh` して確かめる。鍵も画面も向こうへ渡さず、接続を相乗りしない
- **向こうの sh の名乗りには、起動ごとの合言葉を入れる。** 合わない名乗りは採らない（採ると、あとで始末するときに名乗られた別の pid を撃つ）。防ぐのは取り違えで、偽造ではない——向こうのアカウントそのものが悪意を持てば、自分のコマンド行から合言葉を読める
- **向こうの場所はホストごとに許す。** campd は向こうのパスを実パスに直せないので、文字の上で決められること（絶対パス・`..` なし・制御文字なし・`/` そのものは不可）を campd が決め、symlink は向こうの sh が実パスに直してから塞ぐ（許した行のほうも向こうで直して比べる）
- **向こうの sh は `claude` に成り代わらず、親として残る。** 子が終わったら同じセッションの残りを止めてから抜ける（残りが出力を握っていると sshd はチャネルを閉じない）。手元からも、終わったら必ず向こうへ入り直して残りを始末する。boot_id と起動時刻を照らし終えてから、scope にも触る（当初は scope を先に止めていた。codex の指摘）
- **接続が切れても、向こうの子は終わるとは限らない**（stdin を読んでいない子は生き残る。実測）。実行面が見に行って止める。繋がらないうちは「終わった」と書かず孤児にし、繋がり次第止める。終わり方に `conn_lost`（SSH が切れた）を足した
- **campd は向こうのプロセスを確かめられない。** 手元の子なら /proc で起動時刻を見るが、向こうは実行面の報告しか無い。台帳の pid は手元の ssh を指し、向こうの身元は別の列に置く
- **D-025 のなりすましは、見直したうえで受け入れたまま。** なりすました実行面は向こうの記録も偽れる。だが、なりすますにはすでに本人のユーザーで何かが動いている必要があり、それは鍵を持っているので Camp を通さずにどこへでも入れる。増えるのは手元と同じく「記録を偽れる」ことだけ。一方、Camp の API を経由した誤用（Cookie を盗られた場合など）は、許した接続先×許した場所の中に閉じる
- **`/proc` の無いホスト（macOS 等）では起こさない。** 接続が切れたあとに向こうを確かめる手段が無く、確かめられないものを「終わった」とも「走っている」とも書けない。当初は起こしていて、確かめようがないときに「終わった」と書いていた（codex の指摘）。macOS で `ps` から同じことをするには、pid の使い回しに耐えることを実機で示してから
- started が campd に届く前に campd が落ちても、実行面が引き取り直しのときに向こうの身元も名乗り、台帳と照らしてから採る（当初は名乗らず、向こうの pid を永久に失う窓があった。codex の指摘）
- **入れていないもの**: 向こうの会話記録（`~/.claude/projects`）の取り込み。Windows・fish など sh と互換でないログインシェル。dash・BusyBox ash での確かめ（この VM には無く、bash の POSIX モードでしか走らせていない。Termux の sh は未確認）

## D-027: 終わったセッションは「どう終わったか」を決まった語で残す（2026-09-11）

本人の頼み: 終わったものを全部見られるようにし、動いていたセッション・承認待ちのまま放置されて終わったセッションがどれか分かるようにする（D-025 の「実行面が落ちると子も終わる」を仕様にするのと同時に）。それまでは `exit_reason`（自由な文）しか無く、後から選り分けられなかった。

- `end_cause` … なぜ終わったか。9語（`self` / `user_stop` / `idle_timeout` / `turn_timeout` / `stop_timeout` / `start_failed` / `agent_lost` / `unseen` / `reaped`、`internal/session/end.go`）。文は画面と CLI が作る
- `end_state` … 終わる直前に何をしていたか。`stopping` / `orphaned` の**手前**を採る。「止めた」「見張りが外れた」だけでは、動いている途中だったかが分からない
- **Camp が止めろと言ったなら、その理由を控えておき、子が終わったときにそれを採る。** 止めろと言って止まったものを「子が自分で終わった」とは書かない。止まらずに諦めたとき・起こせなかったとき・始末したときは控えより優先する
- 承認の内訳（待たせたまま終わった・期限切れにした）は `approvals.reason` から数える。別の列に写さない
- **9/11 より前に終わった行は空のまま。** `exit_reason` の文から推し量って埋めない。画面では「記録なし」

作る途中で、中断（interrupt）が状態を `stopping` にしたまま戻さないのを見つけた。中断した途端に入力を受けなくなり、2分後には「止まらない」として生きている子を `exited` と書いていた。**中断は状態を変えない**ようにし、中断が効かないターンはしばらく待って孫まで止める。

## D-026: 許可リストは既定で全部拒否。変更には再認証。SSH は Camp の台帳で持つ（2026-09-03）

## D-023: 検出器は入れ物を跨ぐ。Phase 1 で走査されない場所が増えた（2026-09-02）

D-019 は「`messages` を走査し、パターンで取れないものは `known-secrets.txt` で突き合わせる」と決めた。走査対象が `messages` だけなのは、当時それしか無かったから。

**Phase 1 でノート本文が `blobs` に入り、同じ秘密が走査されない場所にもう1つ増えた。** 実測: Vault の平文パスワードは `messages` 25件と `blobs` 1個の両方にある。片方だけ見て「無い」と言うのは検出器として壊れている。

**→ `sensitive_findings` が `blobs` も指せるようにした（0012）。**

- `message_id` の NOT NULL を外すにはテーブルを作り直すしかないが、ここには**人が付けた判定**（`reviewed` / `verdict`）が乗っている。migration で必ず引き継ぐ（14行の判定を維持することを確認済み）
- `CHECK ((message_id IS NULL) <> (blob_sha256 IS NULL))` — 片方だけを指す。両方 NULL は「どこの話か分からない所見」、両方入りは二重計上
- ユニーク索引は**部分索引**になる。`ON CONFLICT` の側にも同じ `WHERE` を書かないと "does not match any PRIMARY KEY or UNIQUE constraint" で落ちる
- 一覧では blob 由来の所見に**出どころ**（`note <パス>` / `backup <パス>`）を付ける。ハッシュだけでは人が追えない

**広げた直後に実在の秘密が1件見つかった。** `Data/Notes/あるサービスのフェデレーション…md` に ActivityPub 署名鍵の PEM 断片。ただし base64 64文字＋省略記号で、2048bit RSA の約1,600文字には遠く**復元できない**。残り6件は SQL 中の `"privateKey"` という文字列そのもの。

走査は 33,621メッセージ + 4,859ブロブ / 183.3MiB を 3.3秒。

## D-022: 残量の記録だけ Phase 0 に前倒しする。D-007 は取り消さない（2026-09-02）

D-007 は「制御プロトコル（`rate_limit_event` / `get_usage`）のほうが statusLine より豊富」と結論した。それは正しい。だが**取得の話と保存の話を混ぜていた。**

Camp が保持しているものは全部、取り込みが遅れても失われない:

| 素材 | 実体 | 遅れて取り込めるか |
|---|---|---|
| 会話記録 | `~/.claude/projects/**.jsonl` | ○ ディスクに残る |
| 編集前の中身 | `~/.claude/file-history/` | ○ ディスクに残る |
| **プラン残量** | **どこにも書かれない** | **× その瞬間しか無い** |

statusLine コマンドは描画のたびに `rate_limits.five_hour.used_percentage` と `resets_at` を stdin で受け取り、**整形して捨てている**。過去に遡って作り直す方法は無い。実際、この値が会話記録に残るのは429を踏んだときだけで、83ファイル中1回しか見つからない。

一方 D-007 の経路は `claude -p` が動いていて初めて使える＝Phase 3。**Phase 3 まで待つと、それまでの窓は永久に空白になる。**

**→ 記録だけ先に始める。表示は最小限。**

- `usage_windows` の UNIQUE は `(agent, kind, ends_at, source)` で **source を含む**。のちに `source='control'` の行が同じ窓に並んでも、`source='statusline'` の記録を上書きしない
- 窓ごとに1行へ畳む（statusLine は毎描画走るので、1観測1行にすると1日で数千行になる）。`peak_pct` と `samples` を足したのはそのため。7日枠は観測が飛ぶと値が下がって見えることがあり、**「あの窓で壁に当たったか」は最新値からは言えない**
- どれが「現在の窓」かは `ends_at` の遠さではなく `fetched_at` の新しさで決める。リセット時刻が動くと、期限だけ先の古い行がいちばん未来に見える
- フックは**失敗を全部握り潰してバックグラウンドに投げる**。campd が無くても DB が壊れていてもプロンプトは今までどおり出る（プロンプトを壊すのは記録できないことより悪い）
- 画面には必ず**観測時刻**を添える。TUI を開いていない間は更新されないので、値だけ見せると古さが分からない。記録が無いときは `0%` ではなく理由を出す（残量ゼロと読めてしまう）

**制約（D-005 から引き継ぎ）:** statusLine は対話TUIでしか発火しない。`claude -p` 単独では記録されない。ただしレート制限はアカウント単位なので、どこか1つTUIが開いていれば足りる。

## D-021: 構築中の入口は使い捨てトークン。パスワードを別経路で流さない（2026-09-02）

構築中は毎回ログインを頼むのが邪魔になる。かといってパスワードを渡す・打ち込ませる経路を作ると、それ自体が漏れる面になる。**トークンを発行できるのは `data/camp.sqlite` に書ける者だけ**で、その者はもう `messages` も `auth_credential` も好きにできる。つまり「シェルが取れる者だけが入れる」という既にある事実を使うだけで、**権限を1つも増やさない**。jupyter や code-server の起動時トークンと同じ形。

```
$ campd login-url
http://127.0.0.1:8785/login?t=…
1回だけ使える。18:12:26 まで（2m0s）。
```

- **1回使ったら死ぬ。** 判定は「未使用かつ期限内の行に印を付ける」UPDATE 1本。読んでから書くと、同じトークンで2回入れる隙間ができる
- **既定2分。** URL に載る以上ブラウザの履歴に残るので、短く切る
- **通ったら素の `/` へ送り直す。** トークンをアドレスバーに残さない
- token そのものは保存しない（`auth_sessions` と同じく SHA-256 だけ）

**パスワードの経路は変えていない。** `campd passwd` で設定し、ブラウザのフォームから入る。使い捨てトークンはそれと並ぶ別の入口であって、置き換えではない。

## D-020: 認証は「/healthz 以外は全部通さない」。画面の殻も配らない（2026-09-02）

D-011 の実装。ゲートは `serve` の1本だけで、そこを通らない経路を作らない。順番に意味がある。

1. セキュリティヘッダ（何を返すにせよ必ず付ける）
2. `/healthz` だけ素通し
3. オリジン検証（状態を変える要求のみ）
4. ログイン経路2つ（`GET /login`・`POST /api/login`）
5. 認証
6. 振り分け。未マッチの GET は殻を返す

**画面の殻とバンドルも認証の内側に置いた。** 「静的ファイルは認証不要」にすると、`index.html` とJSバンドルが誰にでも読める。中身のデータは入っていないが、何が置いてあるかを見せる理由も無い。代わりに `/login` に**組み込みのログイン画面**を持たせた（`internal/httpapi/assets/`）。これで「殻を配らないとログインできない」という循環が消える。未認証のとき `/api/*` は 401 JSON、それ以外は `/login` へ 302。

**保存するのは Cookie の値そのものではなくその SHA-256。** DB を読めた者がそのままログインできるのでは、認証を置いた意味が薄い。パスワードは PBKDF2-HMAC-SHA256・60万回（OWASP の推奨値、Go 1.24 以降の標準ライブラリ `crypto/pbkdf2`）。**パスワードを変えたら開いている口を全部閉じる。**

**オリジン検証は状態を変える要求だけに掛ける。** CORS ヘッダは一切返さないので、他所からの**読み取り**はブラウザ側で止まる。止まらないのはフォーム投稿なのでそこを見る。`Origin` が無いときは `Sec-Fetch-Site` を見て、それも無ければ非ブラウザ（curl 等）とみなして通す。**`X-Forwarded-Proto` は信用しない**ので、比べるのはスキームを剥がしたホストだけ。

**総当たりに抵抗する。** パスワード1本が唯一の壁なので、15分に10回間違えたら 429 を返す（プロセス内で数える。単一ユーザー・単一プロセスなのでこれで足りる）。

**catch-all は `/api/` を除く。** 未マッチの `/api/*` に殻（HTML）を返すと、JSON を待っている相手が原因の分からない壊れ方をする。ここだけ 404 JSON にする。

**CSP で外への発信路を塞ぐ。** トランスクリプトには任意のテキストが入り、そこには他所のURLもスクリプトの断片も混ざっている。`default-src 'self'` と `connect-src 'self'` を効かせておく。

## D-019: 検出器の位置は `raw_json` のバイト位置で持つ。既知の秘密は別経路で突き合わせる（2026-09-02）

D-010 の「破壊しない検出器」の実装。走査しても `raw_json` は1バイトも変えない（33,621件のSHA-256が走査前後で一致）。

**パターン検出はこのコーパスで偽陽性100%・偽陰性100%だった。** D-010 の時点（165MB）で10件だったものが、いまは14箇所／10メッセージ:

| パターン | 箇所 | メッセージ | 中身 |
|---|---|---|---|
| `ghp_[A-Za-z0-9]{36}` | 1 | 1 | pre-push フックのリーク試験で書いた**明示的にダミー**のトークン |
| `-----BEGIN … PRIVATE KEY-----` | 13 | 9 | あるサービス の `user_keypair` を直す SQL・Python・シェルの中の**パターン文字列そのもの**。ヘッダのあとに鍵本体らしい base64 の連なりが続くものは**ゼロ** |

**だから「知っている秘密を突き合わせる」経路を別に置いた。** `known-secrets.txt`（1行 `ラベル<TAB>文字列`）に登録した文字列の出現箇所を `known:<ラベル>` として記録する。中身はリポジトリに置かない（既定は `data/` 配下で gitignore 済み、`CAMP_KNOWN_SECRETS` で差し替え可）。実測: 無害な文字列で試して 369 箇所を検出できた。

> **追記（2026-09-03、M22）: 「`raw_json` は無加工で不変」は、条件つきで崩した。**
>
> `campd retain` が、行の中の**索引に入っていない部分**（誰も復号できない
> `thinking` の署名と、`toolUseResult` 側に二重で入っている画像）だけを落とすように
> なった。実データで 3,663 行 33.4 MB。行は消さず、落としたぶんは `tombstones` に残る。
>
> D-010 の主張のうち**「パターン検出でリダクトするのは有害」は変わらない。**
> 崩したのは「不変」のほうで、崩した理由は、**読めないものを永久に抱える理由が
> 無かった**から（実測で raw_json の 30% が画面にも検索にも出ない中身だった）。
>
> **バイト位置の面倒は崩した側がみる。** `campd retain` は落とした範囲を返し、
> `sensitive_findings.byte_offset` を読み替える。落とした範囲の**中**にあった所見は
> 位置を NULL にする（黙ってずらすと、別の場所を指した所見が「確認済み」の判断つきで
> 残ることになる）。`verdict` は消さない。`campd doctor` に「所見が raw_json の外を
> 指していないか」の点検を足した。
>
> なお 2026-09-03 の実施時点で、落とした 3,663 行に刺さっていた所見は 0 件だった。
> **たまたま無事だっただけなので、仕組みのほうを直した。**

**位置は `block_id` ではなく `raw_json` のバイト位置で持つ。** スキーマには `block_id` 列があるが使わない。`message_blocks` は `campd backfill` のたびに全削除・再挿入で id が振り直される（実測 16,830 → 16,976）。`sensitive_findings` は**人の判断（`verdict`）を載せる唯一の派生表**で、作り直せない。振り直される id に繋ぐとその判断ごと宙に浮く。`raw_json` は無加工で不変（D-010）なのでバイト位置は動かない。

**素朴なパターンを足さないこと。** 実測（162MiB）で `password\s*[:=]\s*…` が47箇所、長い base64 の連なりが 15,773箇所・全メッセージの21%に当たる。当たりすぎる検出器は無視されるようになり、無視される検出器は無いのと同じ。

**取り込みには組み込まない。** 全走査に2.8秒かかる一方、追記なしの `campd ingest` は323ms。ポーリングで回す経路に載せる重さではない。`campd secrets` を明示的に叩く。

## D-018: バックアップの実体は `(session_id, backup_name)` で持ち、素性は delta と snapshot の両方から採る（2026-09-02）

`~/.claude/file-history/<sessionId>/<hash>@v<N>` を DB に取り込む。実測18セッション809個15.5MiB。

**名前は鍵にならない。** 809個のブロブに対して名前は618種しかない。ハッシュはパスから作られるので、同じファイルを複数のセッションが触れば必ずぶつかる（実際に並んで存在する）。名前を鍵にすると素性が混ざり、片方の実体が消えても、もう片方が残っているせいで消滅に気付けない。

**参照元は2つあり、片方では足りない。** `backupFileName` の載り方が版で分かれている:

| 参照元 | version | 件数 | 一意パス |
|---|---|---|---|
| `file-history-delta` の `backup` | 1 のみ | 172 | 92 |
| `file-history-snapshot` の `snapshot.trackedFileBackups` | 2〜28 | 637 | 283 |

M8（ノート↔セッションの結合）では snapshot を読まなかった。展開すると4,754行になるのに新しいパスが1つも増えなかったからで、その判断は結合の話としては正しい。だが実体の素性は逆で、**delta だけ読むと809個中637個が「参照なし」に落ちる**。同じデータ源でも、何を取りたいかで読むべき側が変わる。

**実体とJSONLの突合は現時点で完全な1:1。** 参照はあるのに実体が無いもの0件、実体はあるのに参照が無いもの0件。それでも `origin='orphan'`（`abs_path` は NULL）を用意しているのは、JSONL が先に消えて実体だけ残る順序がありうるため。中身を拾わない理由がない。

**保管は内容アドレス＋日和見圧縮。** `blobs.sha256` は展開後の中身のハッシュなので `codec` に依らず、重複（58個）は1本に畳まれる。809個15.5MiB → blobs 751本4.7MiB（DBのページ実測 5.5MiB）。809個すべてディスクとバイト単位で一致することを確認済み。

**実体が消えたら `missing_at` を立てるだけ**（D-001と同じ扱い）。行も中身も消さない。ここから先はCamp にしか無い。実例: `Obsidian-vault`（小文字v、2026-08-09に改名されて**ディレクトリごと存在しない**）配下の `Human/Projects/ExampleProject.md` は、v2〜v5 の4版・3,627行が Camp からそのまま読める。

**素性は作り直せる**（D-014）。`campd backfill` が `messages` から `abs_path`・`rel_path`・`version`・`origin` を再計算する。中身はディスクからしか取れないので `blobs` には触らない。

## D-017: `file-history` の繋ぎ先は取り込み中には決まらない。読み終えてから繋ぎ直す（2026-09-02）

`file-history-delta` は自分の `uuid` も `sessionId` も持たず、`messageId` で「この編集を出したアシスタント行」を指す。素直に読むと「取り込みの最中にその uuid を引けばよい」となるが、**実測では 403件中 372件で、バックアップの記録のほうがアシスタント行より先に書かれていた**（前にあるのは31件だけ）。前から順に読む取り込みでは、その時点で繋ぎ先がまだ存在しない。

その場で引く実装だと、31件だけ繋がって372件が繋がらない、という中途半端な状態になる。しかも `campd backfill`（全行が揃った状態から作る）とは結果が食い違う。**同じ入力から2つの経路が違う答えを出すのが一番まずい。**

なので繋ぎ先はその場では決めない。いったん `file-history` 行自身を指しておき、読み終えてから `LinkFileHistory` が1本の UPDATE で繋ぎ直す。繋ぎ直したあとの指し先は `assistant` なので、この UPDATE は二度目以降1行も動かさない。取り込みを跨いだ場合（delta だけ先に入り、アシスタント行が次の実行で来る）も次の実行の最後に拾われる。

**検証:** 空のDBへ丸ごと取り込んだ結果と、既存DBを `backfill` した結果を突き合わせて、2,414行が `session_id` / 繋ぎ先の uuid / `abs_path` / `rel_path` / `op` / `origin` / `backup_name` / `at` のすべてで一致した（差は、あとで走らせた側が1件新しい記録を拾ったことだけ）。file-history 403件の繋ぎ先はすべて `assistant` 行である。

## D-013: `usage` は「最初の1行を採る」ではなく列ごとの `max` を採る。`day` はローカル日付（2026-09-02）

**受け入れ条件に書いた `ON CONFLICT DO NOTHING` は間違いだった。**

同じ `api_message_id` が複数行に現れる理由は2つあって、扱いが違う。

| 理由 | 現れ方 | 正しい扱い |
|---|---|---|
| ストリーミングの途中経過 | 同じファイルの中に、出力が伸びていく途中の行が並ぶ | 最後（＝最大）が確定値 |
| fork / resume の複製 | 別ファイルに、まったく同じ数値でもう一度現れる | どれを採っても同じ |

実測（2026-09-02）: `api_message_id` 7,101個のうち **48個で `output_tokens` が行ごとに違う**。`input_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens` が食い違う id は**ゼロ**。つまり伸びるのは出力側だけ。時刻順に並べたとき出力が減る箇所も**ゼロ**（単調増加）。

最初の1行を採ると出力が **4,630,878**、`max` を採ると **4,667,284**。36,406トークンの過少計上になる。

**採用:** 列ごとに `max` を取る upsert。`max` は順序に依らず冪等なので、途中経過と確定値が別々の取り込みパスに分かれても結果が変わらない（差分追尾では実際に分かれる）。

**`<synthetic>` は `usage` に入れない。** CLIがローカルで作る擬似アシスタント行で、`usage` は常にゼロ、課金も発生していない。入れておいて集計のたびに除外するより、最初から入れないほうが「除外を忘れる」経路が消える。`messages` には残す（実測16行）。

**`day` はUTCではなくホストのローカル日付にする。** JSTだと15:00Z以降は翌日で、UTCで切ると「今日どれだけ使ったか」が毎日9時間ぶんずれる。プラン上限の話をしたいのだから、区切りは人間の1日に揃える。

**`usage.iterations` は整数ではなかった。** `usage` と同じ形のオブジェクトの配列で、実コーパスでは長さが必ず1、その唯一の要素は上位の `usage` と完全に一致する（11,468行すべてで `output_tokens` も `cache_read_input_tokens` も一致）。上位がロールアップで配列がその内訳。長さ2以上の実例をまだ見ていないので、**上位が内訳の合計なのか最終イテレーションなのかは未確認**。いまは本数だけ持つ。

**同じ id が複数セッションに現れたときは最初に取り込んだほうに帰属させる。** トークンは1回しか払っていないので、fork した側の複製ぶんが0になるのはむしろ正しい。

## D-012: run とセッションは多対多。`runs.session_id` を捨てて `session_runs` を作る（2026-09-02）

**D-001 の時点で組んだ「1セッションが複数の run を持つ」という片方向の関係は間違いだった。**

M2 の実装中、`runs` の挿入試行42回に対して行が33しかできないことに気づいて追ったところ、**1つの run が複数のセッションを生む**経路が見つかった。

実測（`unibridge`、2026-09-02確認）:

| run | 生んだセッション | 期間 |
|---|---|---|
| `bf4ff50f-…` | **8** | 2026-08-02T11:59 → 08-08T10:09 |
| `23758181-…` | 2 | 08-12T02:27 → 08-12T19:10 |
| `a46a0092-…` | 2 | 08-10T08:01 → 08-10T11:35 |

`bf4ff50f` の8ファイルは**隣り合う末尾と先頭のタイムスタンプが25ms以内で連なり、8本すべてがちょうど1回の `/clear` を含む**。つまり `/clear` は会話ファイルを新しくするが CLI の実行IDは変えない。しかも `bf4ff50f` という名前の `.jsonl` は存在しない。逆に session `9182f0fd` は4つの run を持つがそのどれも自分のIDではない（`/clear` で生まれた側だから）。

- 1セッション : 多run … `--resume`
- 1run : 多セッション … `/clear`

**片方向だと思うと、`runs` に「持ち主のセッション」を1つ選ばせることになる。** 実装は最初そうなっていて、8セッションのうちアルファベット順で最初のものを恣意的に選んでいた。さらに `messages.run_id` をセッション単位で照合していたため、**19,577件あるべき run 紐付きメッセージが12,404件に落ちていた**（7,173件の取りこぼし）。

**採用:** `runs` は実行そのものだけを持ち、`session_runs(session_id, run_id, seq)` で対応を張る。`seq` はそのセッション内での実行順（0 = 初回、以降 `--resume`）。run 側から見ると「この一続きの実行が生んだ会話たち」が辿れる。

`0001_init.sql` を書き換えて反映した（マイグレーションの追記ではなく）。**まだどこにもデプロイしておらず、コーパスは6秒で作り直せる**ため、`ALTER TABLE RENAME` で `messages.run_id` の参照先が書き換わる罠を踏むより初期スキーマを正すほうが安全だと判断した。

## D-010: raw_json は生のまま保存する。リダクトしない（2026-09-01）

**実データで検証した結果、リダクトは有害と判明した。**

`.githooks/pre-push` の高信頼パターンで現在の165MBを走査したところ、`ghp_` 1件・`BEGIN … PRIVATE KEY` 9件がヒットしたが、**10件すべて偽陽性**だった。全部が `tool_use`（Bashコマンド）内のパターン文字列そのもので、鍵の本体が続くものはゼロ。おそらくpre-pushフック自体を書いていた時のコマンド。

**素朴なパターンリダクトを入れていたら、10件の正当なレコードを壊して得るものはゼロだった。**このコーパスでの誤検出率は100%。加えてCampの主目的は「後で探せること」なので、価値の大半がある `tool_result`（55.9MB）を壊すのは自己矛盾になる。

**採用する方針:**

- **生のまま保存する**
- **破壊しない検出器を置く。** `sensitive_findings` テーブルに「ここが引っかかった」だけ記録し、消さない。後から個別に判断できるようにする
- アプリ認証を入れる（D-011）
- SQLiteの保存時暗号化は鍵が同じ箱にある以上**バックアップ流出にしか効かない**。バックアップを外部に置く場合のみ検討する

**却下:**

- 危ない部分だけ暗号化 → 検出問題と同じもの。特定できないから困っているので、暗号化に置き換えても偽陰性率は同じまま鍵管理だけ増える
- 1Password等との連携 → シークレットマネージャが解くのは「**使う**シークレットをどこに置くか」で、「**漏れた**シークレットをどうするか」ではない。既にトランスクリプトに入ったものを後から金庫に入れることはできない

**Camp外の関連タスク（今日いちばん効く一手）:** Vault のあるノートに平文パスワードがある。ここをシークレットマネージャ参照に置き換えれば、以後のセッションは平文を持たなくなる。これはVault側の衛生の話でCampの機能ではない。

## D-001: 履歴は自前SQLiteへ複製し、元が消えても行を消さない（2026-09-01）

「独立して保持」の核心。CLI側でJSONLが消えても行は削除せず、消えた事実だけ記録する。
